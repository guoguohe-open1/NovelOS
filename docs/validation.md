# 验证策略与长篇实验

## 1. 验证原则

首先证明数据和创作过程可信，再评价文笔。工程检查以确定性 Fake、真实 PostgreSQL 集成和少量端到端流程为主；真实模型只用于适配与创作实验，不作为默认测试依赖。

T00 已建立工程骨架和最小健康、配置、PostgreSQL 迁移测试；命令见根目录 README，执行证据与限制见 [T00 验证记录](t00-validation.md)。下列业务场景仍是待实现规范，不能视为已通过；T09 再验证完整 MVP 的干净环境执行。

## 2. 关键验收场景

| ID | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| V01 | 干净环境启动、迁移与数据库断开 | 可复现启动；不可用依赖使就绪检查失败；迁移不依赖手工建表 |
| V02 | A 项目访问/引用 B 的章、版本、资产与记忆 | HTTP 不能读取或修改；Context Builder 和检索也排除；非法引用无法提交 |
| V03 | 旧正式修订写入或验收 | 返回冲突，正式数据与修订不变；不能通过把请求修订改成新值绕过提案基线 |
| V04 | 非法资产字段、未知插件、越界路径或坏引用 | 在持久化正式数据前失败；不执行外部代码；错误可定位 |
| V05 | 草稿保存、复制候选、回退 | 每次新增不可变版本；不移动正式指针、不递增正式修订；AI 候选不移动草稿指针 |
| V06 | 双标签页保存同一草稿基线 | 仅一次更新成功；后一个收到冲突；UI 保留未保存内容 |
| V07 | 生成/拒绝候选 | 待审与拒绝均不改变正式资产、正文或记忆；候选可追溯 |
| V08 | 验收中途失败、重复点击与并发验收 | 失败全部回滚；重复键重放；不同请求不能让同一提案应用两次 |
| V09 | 提交请求超时后重放、同键不同正文 | 相同请求返回原资源；不同请求冲突；不会重复启动模型 |
| V10 | API/worker 重启与租约过期 | 任务持续可查；成功步骤输出可复用；丢失租约的旧 worker 无法推进任务；未知外部调用不被自动重发 |
| V11 | 模型已发出、结果未持久化时崩溃 | 标明结果/计费未知，不盲目重发；人工重试是新任务 |
| V12 | 限流、临时失败、认证错误与坏 JSON | 有限重试，修复计入尝试；认证/能力错误不自动重试；失败保留用量 |
| V13 | 连续失败耗尽调用/token预算 | 发起下一请求前停止；不得自动提高预算；未知用量不按零计算 |
| V14 | 取消与模型返回/形成提案/验收并发 | 锁下决定单一合法结果；取消后不启动新步骤；已验收结果不能被取消撤销 |
| V15 | 资料含越权提示、敏感配置 | 资料不能获取新工具或密钥；前端与日志没有密钥或默认完整正文 |
| V16 | 最终稿被人工修改或上下文发生正式变动 | 旧提案过期且不能验收；新版本重新审阅；摘要与提取来源等于最终验收正文 |
| V17 | 回写前章/历史资产，检索与后续重验收 | 下游被标记失效；旧来源不进入检索；按序重审后恢复，早期章不读未来状态 |
| V18 | 计数、快照导出、备份恢复 | 只统计有效正式版本；章序正确；失效章阻断整书导出；恢复保留来源与历史 |

对并发、事务与租约使用真实 PostgreSQL 运行集成检查，不能仅用内存库或 SQLite 推断其正确性。外部供应商请求通过可控适配器模拟完成、超时和未知结果。

## 3. 分层测试

- **领域单元**：状态转移、章序、生效边界、资产 schema、计数规则、ChangeSet 操作白名单。
- **应用集成**：项目隔离、复合引用、验收事务回滚、草稿竞争、正式修订竞争、历史失效与恢复。
- **任务恢复**：在“已保存请求”“已获得输出”“已保存检查点”等位置注入故障，检查是否重用结果或明确停止为未知。
- **接口契约**：状态码、错误码、分页、幂等语义、字段联合类型；生成 OpenAPI 后检查前端类型一致性。
- **Web 端到端**：建项目到两章验收；人工改稿；失败/取消恢复；双标签页冲突。避免为每个展示标签编写脆弱快照。

纯文档变更检查本地链接、锚点、代码块示例、术语和契约一致性，不为不存在的业务实现补造测试结果。

## 4. 真实模型适配验证

在明确启用的集成任务中验证供应商响应、结构化输出、超时映射和用量字段。记录供应商、模型精确标识、参数、提示词/规则包版本、时间和已知费用。没有凭据时报告跳过，不将 Fake 测试当成真实模型接入证据。

真实模型输出不要求逐字一致。以 schema、硬约束、来源完整性和人工可用性判断；不把第二个模型给的高分当作唯一验收证据。

## 5. 10 万字实验方法

### 准备

固定题材包、初始人物/规则、卷章目标、风格、模型配置和预算；保存实验起始正式修订。挑选可核查的事实、能力边界与长距离伏笔，建立作者维护的检查表。指标定义在实验前确定，避免事后只选择好看的结果。

### 记录

每章记录输入快照、候选数、是否重写、失败/重试类别、模型用量、未知计费、作者修改和验收时间。正文修改幅度可用字符差异比例辅助描述，但它不能独立代表质量。

字数口径是有效已验收版本内的汉字数，另报总字符数和章数。历史版本、被拒绝候选、失效章不计入 10 万汉字门槛。

### 评估

| 维度 | 检查方法 | 报告内容 |
| --- | --- | --- |
| 工程完整性 | 全量检查版本、提案、来源与修订链 | 缺失/异常数量；关键不变量违规必须为 0 |
| 人物与世界一致性 | 对预设事实和长距离状态做人工抽查 | 样本分母、冲突数、影响与修复过程 |
| 伏笔与规划 | 对检查表逐项跟踪埋设/回收/延期 | 未回收原因、作者决策，不用模型自行认定成功 |
| 章节可用性 | 作者逐章记录可用、需局改、需重写及原因 | 各类数量与典型片段；不声称商业留存效果 |
| 成本与恢复 | 汇总尝试、token、估算费用、未知项和恢复事件 | 每有效千汉字的用量与费用、总耗时、人工时间 |

实验达到字数与工程完整性门槛后，仍应诚实报告创作质量缺陷。未达到质量预期时，先调整上下文/规划/审阅策略并重测，不立即堆叠 Agent 或引入更复杂基础设施。

## 6. 结果归档

实现阶段建立包含环境、命令、结果、失败和限制的检查记录。长篇实验另存报告和脱敏配置，正文是否分享由作者决定。任务状态只在相应验收通过后更新；真实模型、10 万字与百万字能力分别声明验证范围。
