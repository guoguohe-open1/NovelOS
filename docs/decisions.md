# 关键设计决策

记录日期：2026-10-21。D01–D08 保留设计整理时的**基线选择**；T00 只落地工程基础，业务与长篇实验尚未验证。实施补充追加为新记录，实际验证见 [T00 记录](t00-validation.md)。变更时保留原决定、原因与替代结果，避免仅改一段技术栈列表。

## D01：先建模块化单体

**背景**：样稿分别提出平铺目录和多个 `packages/*`，尚无可复用代码或部署需求。

**选择**：Web 单独工程；后端用一个 Python 包表达领域、应用、Agent 和基础设施边界；HTTP 与 worker 分进程但共用代码和数据库。

**代价**：需要用导入约束和审阅保持边界，无法独立扩缩每个领域模块。

**重审条件**：出现独立发布、明确资源瓶颈或其他应用需要复用某个包。详见 [架构](architecture.md)。

## D02：PostgreSQL 是唯一权威存储

**背景**：样稿将任务状态放 Redis，记忆放 Qdrant，又未说明持久性、双写和恢复。

**选择**：任务、检查点、正文、资产和正式记忆先进入 PostgreSQL；初期用结构化与关键词检索。Redis/Qdrant 以后作为可重建派生设施。

**代价**：语义召回初期有限，数据库任务领取需要实现租约与索引；不能依赖缓存获得吞吐收益。

**重审条件**：实测检索漏召回或任务吞吐成为瓶颈；引入时先设计 outbox、回放和来源过滤，不切换事实权威。

## D03：显式持久化状态机先于编排框架

**背景**：样稿直接指定 LangGraph，但没有状态、检查点和人工等待契约。

**选择**：先定义并实现有限工作流、检查点、预算和恢复；不把 LangGraph 作为 MVP 前置条件。Agent 可以是普通函数，只要符合协议与权限。

**代价**：自建简单调度需要维护；以后接框架可能需要适配。

**重审条件**：分支、暂停恢复、并行节点显著增多，框架能减少实际维护成本。框架不能替代数据库验收事务。

## D04：候选、人工验收与正式记忆分离

**背景**：样稿生成后直接更新人物/世界，容易把废稿变成后续事实，也未处理人工改稿。

**选择**：生成不可变候选和有限 ChangeSet；作者在版本校验后原子验收。手工正文通过独立审阅任务提取记忆，修改后重新审阅。

**代价**：多一步人工操作；需要保存提案、版本、用量和输入快照。

**重审条件**：可以为低风险任务设计预授权自动验收，但必须独立定义适用范围、审计与撤回；MVP 不提供此能力。

## D05：正式资产采用有类型的版本化模型

**背景**：人物、世界、事件、伏笔都需要版本、来源和生效边界；样稿各自字段稀疏且缺少统一修订规则。

**选择**：`StoryAsset` 提供身份与类型，`AssetVersion` 保存受 schema 约束的类型字段；关键关系字段用关系数据库约束。正文独立版本化，不复用万能文本版本表。

**代价**：JSONB 字段需要显式 schema 和迁移策略，部分复杂查询不如独立专表直观。

**重审条件**：出现稳定高频的跨人物关系/事件查询或严格字段约束需求，按实际查询拆专表；保持资产 ID 和历史可迁移。

## D06：题材插件先作为固定版本数据规则包

**背景**：“所有功能必须插件化”和含任意 `tools/agents/` 代码的插件目录会扩大首版工程与权限面。

**选择**：核心创作流程是平台能力；玄幻包仅提供 manifest、schema、规则与测试样本。题材和风格分离，风格先作为结构化配置。

**代价**：暂不能安装自定义 Python Agent 或任意外部工具；扩展规则需遵循已有 schema 扩展点。

**重审条件**：真实题材无法用规则/schema 表达时再设计受控执行接口。不能通过插件越过正式写入和模型网关。

## D07：按章节边界读取记忆，历史修订使下游失效

**背景**：只存人物“当前状态”会把第 100 章事实注入第 2 章；回退正文也不等于回退记忆。

**选择**：资产版本/记忆带生效边界与来源。替换前章或历史设定时使受影响后章和记忆失效，作者按序重新审阅。MVP 不做自动剧情分支与连锁重写。

**代价**：修订历史可能需要较多重新确认；查询必须考虑来源有效性。

**重审条件**：作者频繁需要并行分支或大规模倒叙编辑时，再设计分支时间线与增量依赖分析；不能只加一个 `parent_version` 字段就声称具备 Git 式分支。

## D08：将 10 万字作为实验门槛

**背景**：长期百万字目标与“生成第一卷”“十万字闭环”在样稿中交替出现，容易变成无法验收的大任务。

**选择**：先验收单章工程闭环，再用实际模型与作者完成 10 万汉字实验，最后决定语义检索、导演与百万字能力的下一阶段。

**代价**：早期不展示复杂图谱和全自动长篇承诺；需投入作者评审与实验成本。

**重审条件**：实验揭示清晰瓶颈或产品目标改变；以报告而不是单次演示决定扩展。

## D09：T00 使用显式环境配置与无业务表基线迁移

**背景**：仓库根目录已有用户 `.env`；T00 需要可复现本地工程，同时不能读取或覆盖它，也不能越过 T01 设计业务表。

**选择**：用 npm 和 uv 锁定两个工程；后端只读取进程环境，命令显式选择脱敏 `.env.example`，Compose 同样显式指定环境文件。Next.js 工程位于 `apps/web`，根目录 `.env` 不作为它的配置入口。初始 Alembic 修订只建立迁移历史；不建立示例业务表，不在 API 启动时执行迁移。健康就绪只执行数据库查询，迁移由单独命令验证。

**代价**：需要显式选择配置文件和先迁移再启动；当前机器无 Docker 引擎时，真实 PostgreSQL 验证不能证明容器启动成功，必须分开记录。

**重审条件**：引入业务表、部署流程或新的配置来源时再扩展检查；保留启动/迁移分离、敏感信息不进前端和不隐式加载根目录配置的边界。

## D10：原生数据库为默认，Docker Compose 改为可选

**背景**：此前 T00 将 Compose 启动列入验收，但本机缺少 Docker 引擎；原生 PostgreSQL 17.11 的迁移、健康检查和故障恢复已经验证。用户明确要求可以不打包 Docker，优先直接在本机运行。

**选择**：Web、API 和 PostgreSQL 默认以原生进程运行，提供 Windows 便携与已有数据库服务的操作说明。保留 PostgreSQL Compose 文件作为可选路径，不新增应用 Dockerfile，不要求安装 Docker。两种路径共享数据库版本、连接配置、迁移和测试；T00 / M0 依据默认原生路径验收，容器路径的未验证状态单独保留。

**代价**：开发者需要安装或解压 PostgreSQL，按说明管理数据目录、账号和进程；不同平台的原生安装步骤存在差别。原生验收不证明 Compose 数据卷与容器启动通过。

**重审条件**：出现统一分发、容器部署或跨平台环境标准化的明确需求时，再验证并启用容器路径。此决定替代此前“容器启动是 T00 前置条件”的要求，不改写原失败记录。

## D11：按验证完成的逻辑单元提交，本地身份与远程认证分开

**背景**：用户要求初始化 Git、确认账号，并在合适时机维护 Git 和提醒其推送；机器原有全局署名属于公司身份，连接器的个人 GitHub 账号并不代表本机已认证。

**选择**：使用本地 `main` 分支、仓库级提交身份和标准忽略规则；验证通过的完整改动主动创建本地提交。远程仓库由用户明确提供或创建，完成基线或任务后提醒用户推送，默认不代替执行。远程未创建时不绑定猜测地址、不把连接器登录当作 CLI 推送证明。

**代价**：首次推送需要用户创建目标仓库并完成本机认证；新克隆需要自行设置提交身份。

**重审条件**：用户明确授权代为推送、改变分支协作方式或引入 CI / 多人协作后，更新 [Git 工作流](git-workflow.md)；不以自动化为由默认改写历史或强推。
